# ops-bot

Telegram-бот (.NET 10, webhook) для керування всіма власними сервісами на хості та **стандарт розгортання**, за яким ці сервіси живуть. Бот показує стан сервісів, розгортає нові версії з артефактів, відкочує на попередні, показує список змін до й після розгортання та причину помилки.

Один бот обслуговує всі сервіси хоста, розгорнуті за стандартом (§2). Сервіс підключається своїм `setup.sh`, перезапускати бота для цього не треба.

## 1. Як це працює

```
машина власника                       хост
───────────────                       ────────────────────────────────────────────────────────
build.sh ── артефакт ── scp ──▶ /opt/<id>/artifacts/<id>-<VERSION>.tar.gz (+ .sha256)
                                         │
Telegram ◀──▶ ops-bot (без root) ────────┤ читає: app, v*, artifacts, CHANGES.json, systemctl, health
                 │ пише запит            │
                 ▼                       ▼
        data/requests/<id>.req ──▶ ops-runner.path ─▶ ops-runner.sh (root) ─▶ /opt/<id>/bin/deploy.sh
                 ▲                                                               │
        data/results/<id>.{log,done} ◀──────────────────── вивід і код ──────────┘
```

- **Збірка** — `build.sh` проекту на машині власника: тести, `dotnet publish`, `VERSION`, `CHANGES.json`, архів і контрольна сума; `--upload HOST` копіює їх у `artifacts/` сервісу.
- **Розгортання** — `deploy.sh` сервісу (root): розпаковує реліз у `v<VERSION>`, виконує підготовку проекту (наприклад, копію БД і міграції), перемикає `app`, робить смоктест і за потреби відкочується.
- **Бот** працює без прав root. На кнопку «Розгорнути» він лише пише файл запиту, а `ops-runner` (root, systemd `.path`) суворо перевіряє запит і запускає `deploy.sh`.

## 2. Стандарт сервісу

```
/opt/<id>/
├── app -> v1.0.0.845        активний реліз; systemd запускає сервіс через це посилання
├── v1.0.0.845/              релізи: активний і 2 попередні (KEEP_PREVIOUS)
├── v1.0.0.840/
├── v1.0.0.835/
├── data/                    спільні дані всіх релізів (пише лише сервіс)
├── configs/                 конфігурація: service.env, appsettings.Production.json, …
├── artifacts/               артефакти від build.sh --upload
└── bin/deploy.sh            оновлюється з кожного нового релізу (deploy/bin/*)
```

| Шлях | Власник і права | Хто що робить |
|---|---|---|
| `/opt/<id>`, `bin/` | `root:root 755` | — |
| `v<VERSION>/` | `root:<user>`, файли `644`, каталоги `755` | сервіс і бот лише читають; секретів у релізі немає |
| `configs/` | `root:<user> 755` | `service.env` — `644` (читає бот); секрети — `640` |
| `data/` | `<user>:<user> 750` | пише лише сервіс |
| `artifacts/` | власник, що завантажує (`SUDO_USER`) | `build.sh --upload` |

**`configs/service.env`** — параметри `deploy.sh` і бота ([приклад](template/service.env.example)). Це дані, а не скрипт: `KEY=VALUE` без лапок.

| Ключ | Значення |
|---|---|
| `TITLE` | Назва в боті |
| `UNIT` | Юніт systemd (без `.service`), за замовчуванням — id |
| `SERVICE_USER` | Системний користувач сервісу |
| `ENTRY` | Файл, який має бути в кожному релізі (виконуваний файл застосунку) |
| `HEALTH_URL` | Смоктест і моніторинг: відповідь 2xx |
| `VERSION_URL` | Необов'язково: відповідь містить `"version":"<VERSION>"` активного релізу |
| `HEALTH_TIMEOUT` | Секунд на смоктест (60) |
| `KEEP_PREVIOUS` | Скільки попередніх релізів лишати (2) |
| `CONFIG_LINKS` | Файли з `configs/`, які кожен реліз отримує посиланням |

**Юніт systemd** — [приклад](template/app.service.example): `WorkingDirectory` і `ExecStart` через `/opt/<id>/app`, `ConditionPathExists` на виконуваний файл (до першого деплою сервіс не стартує), `ReadWritePaths=/opt/<id>/data`, решта файлової системи лише для читання.

**Спільні файли шаблону** копіюються в проект без змін: [`template/deploy.sh`](template/deploy.sh), [`template/setup-service.sh`](template/setup-service.sh), [`template/changes.sh`](template/changes.sh). Нова версія шаблону — нова копія в кожному проекті.

## 3. Артефакт і список змін

`<id>-<VERSION>.tar.gz` і `<id>-<VERSION>.tar.gz.sha256`. Усередині:

| Файл | Призначення |
|---|---|
| `VERSION` | Рядок 1 — версія, рядок 2 — коміт, рядок 3 — час збірки (UTC) |
| `CHANGES.json` | Список змін українською й англійською (нижче) |
| застосунок | Вихід `dotnet publish --self-contained` для `linux-x64` чи `linux-arm64` |
| `deploy/bin/*` | `deploy.sh` та інші скрипти для `/opt/<id>/bin` |
| `deploy/hooks/pre-switch` | Необов'язково: підготовка релізу перед перемиканням (копія БД, міграції) |

`VERSION` і `CHANGES.json` ідуть першими в архіві: бот читає їх, не розпаковуючи все.

**Версія** — `<Version з .csproj>.<кількість комітів>`, наприклад `1.0.0.845`. Остання частина — номер збірки: за ним бот вибирає зміни між двома версіями. `build.sh` відмовляється збирати з незакоміченими змінами (`--allow-dirty` — лише для перевірки): інакше одна версія означала б різний код.

**Список змін** генерує `template/changes.sh` з історії git (гілка по first-parent, до 100 комітів). Беруться лише коміти, що змінюють файли сервісу (`PATHS` у `build.sh`). Текст — з трейлерів повідомлення коміту:

```
Server runs under systemd with smoke test and rollback

Change-uk: Сервер працює під systemd зі смоктестом і відкатом
Change-en: The server runs under systemd with a smoke test and a rollback
Co-Authored-By: …
```

Коміт без трейлерів дає свій заголовок обома мовами; `Change-uk: -` приховує коміт. Кожна зміна має `build` — номер збірки коміту гілки, що приніс її (для merge — кількість комітів merge-коміту), тож зміни feature-гілки належать збірці, у якій їх злито.

## 4. Розгортання, смоктест і відкат

`sudo /opt/<id>/bin/deploy.sh <артефакт>`:

1. перевіряє контрольну суму, розпаковує в `.incoming.*`, перевіряє `VERSION` і `ENTRY`, перейменовує в `v<VERSION>` (версія має бути новішою за активну);
2. виставляє права, створює посилання на файли з `configs/`;
3. виконує `deploy/hooks/pre-switch` (помилка — реліз видаляється, сервіс не змінюється);
4. перемикає `app` (`ln -sfn` + `mv -T`, одним кроком) і перезапускає юніт;
5. **смоктест**: юніт активний, `HEALTH_URL` дає 2xx, `VERSION_URL` показує нову версію — до `HEALTH_TIMEOUT` секунд;
6. не пройшов — друкує журнал сервісу від моменту перемикання, повертає `app` на попередній реліз, видаляє невдалий;
7. пройшов — встановлює `deploy/bin/*` у `bin/`, лишає активний і 2 попередні релізи, видаляє старіші релізи та їхні артефакти.

`deploy.sh --rollback [VERSION]` — повернення на попередній (або вказаний) реліз зі смоктестом; якщо той не працює, `app` повертається назад. `deploy.sh --status` — релізи й активний.

Коди завершення: `0` — готово; `1` — помилка, сервіс не змінено; `2` — смоктест не пройдено, працює попередній реліз; `3` — не працює і відкат (або попереднього релізу немає, тоді сервіс зупинено). Для бота останній рядок виводу — `@result <код> <деталі>`, а журнал сервісу — між `@journal-begin` і `@journal-end`. Бот перекладає код у причину українською чи англійською:

| `@result` | Причина |
|---|---|
| `ok` | — |
| `locked`, `no-artifact`, `no-checksum`, `checksum`, `extract`, `not-a-release` | інший деплой, немає файлу, контрольна сума, пошкоджений архів, не той сервіс |
| `active`, `exists`, `not-newer` | версія вже активна / вже є / не новіша |
| `config-missing`, `hook-failed` | немає файлу конфігурації / не вдалася підготовка (копія БД, міграції) |
| `rolled-back`, `first-failed`, `both-failed`, `target-failed` | смоктест не пройдено (з деталями: юніт не активний, health не 2xx, інша версія) |
| `no-active`, `no-previous`, `no-release` | для відкату немає релізу |
| `rejected`, `timeout` | `ops-runner` відхилив запит / деплой довше 30 хвилин |

**ops-runner** обробляє `data/requests/*.req` — один рядок `deploy <id> <VERSION>` чи `rollback <id> <VERSION|->`. Він відхиляє (код 126) застарілий запит (понад 15 хвилин), сервіс поза `configs/services`, неправильну версію, `deploy.sh`, який може змінити не лише root. Результат — `data/results/<id>.log` і `<id>.done`.

## 5. Встановлення бота

1. Створити бота в @BotFather, зберегти токен.
2. Скопіювати на хост і виконати setup:
   ```bash
   scp -r deploy template HOST:ops-bot-setup/
   ```
   ```bash
   ssh -t HOST sudo bash ops-bot-setup/deploy/setup.sh
   ```
3. Заповнити `/opt/ops-bot/configs/appsettings.Production.json`: `Bot:Token`, `Bot:WebhookUrl` (публічна HTTPS-адреса), `Bot:AdminIds`. `WebhookSecret` setup генерує сам. Свій Telegram ID бот покаже на `/start`, поки ID немає в `AdminIds`. Якщо хост не бачить api.telegram.org, задати `Bot:Proxy` (`socks5://…`).
4. Реверс-проксі з TLS пропускає назовні лише `POST /telegram/webhook` на `127.0.0.1:8095`. Приклад для Caddy:
   ```
   ops.example.com {
       handle /telegram/webhook {
           reverse_proxy 127.0.0.1:8095
       }
       respond 404
   }
   ```
5. На машині власника:
   ```bash
   deploy/build.sh --upload HOST
   ```
6. Перший деплой — вручну на хості (далі бот оновлює й себе):
   ```bash
   sudo /opt/ops-bot/bin/deploy.sh /opt/ops-bot/artifacts/ops-bot-<VERSION>.tar.gz
   ```

## 6. Підключення сервісу

1. Скопіювати в проект `template/deploy.sh`, `template/setup-service.sh`, `template/changes.sh`.
2. Додати `service.env`, юніт systemd, `build.sh` (за зразком [deploy/build.sh](deploy/build.sh)): `PATHS`, тести, `dotnet publish`, `VERSION`, `CHANGES.json`, `deploy/bin/deploy.sh`, за потреби `deploy/hooks/pre-switch`.
3. Сервіс віддає версію релізу на `VERSION_URL` (`"version":"1.0.0.845"`) — так смоктест бачить, що працює саме новий реліз.
4. `setup.sh` проекту викликає `setup-service.sh <id> <user> <unit> <service.env>` і готує свою конфігурацію; сервіс з'являється в боті.

Приклад — [finance-app/deploy/server](../finance-app/deploy/server/README.md).

## 7. Бот

- `/status` (чи `/start`) — усі сервіси: 🟢/🔴, активна версія, доступний новий артефакт.
- Картка сервісу: юніт (стан, час старту, перезапуски), health, версія, попередні релізи, новий артефакт; кнопки «🚀 Розгорнути», «↩️ Відкотити», «📜 Журнал», «🔄 Оновити».
- **До** розгортання бот показує зміни між активною й новою версією, **до** відкату — зміни, які буде скасовано; дію треба підтвердити.
- **Після** — результат усім адміністраторам: що сталося, причина помилки з деталями, ті самі зміни («Зміни» / «Не розгорнуто» / «Скасовано»), журнал сервісу після невдалого старту.
- Моніторинг щохвилини: 🔴 після 3 невдалих перевірок поспіль, 🟢 після відновлення, 📦 новий артефакт зі списком змін і кнопкою розгортання.
- Мова — українська чи англійська: спершу з налаштувань Telegram, далі кнопка «🌐».

## 8. Безпека

- Бот працює від `ops-bot` без root: читає `/opt`, пише лише `/opt/ops-bot/data`. Розгортання виконує `ops-runner` (root) за файлом запиту, який перевіряє суворо; список сервісів (`configs/services`) належить root.
- Webhook перевіряє `X-Telegram-Bot-Api-Secret-Token`; назовні відкрито лише `POST /telegram/webhook`. Керують лише `Bot:AdminIds` у приватному чаті.
- Секрети сервісів лише в `configs/` з правами `640`; релізи без секретів, читаються всіма (бот читає `CHANGES.json`).
